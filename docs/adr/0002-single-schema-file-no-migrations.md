# A single append-only schema.sql instead of migrations

All DDL lives in one file, `supabase/schema.sql`, which is appended to as the schema grows and
applied by pasting into the Supabase SQL editor. `.clinerules` requires that any edit to it also
produce an isolated `ALTER` snippet for the live database. This was the fastest path for one person
prompting an agent, and it avoided setting up the Supabase CLI.

**Status: accepted, and the first thing to revisit.** It has already cost us.

## Consequences

- **The file and the live database have provably diverged.** `admin_set_is_admin` in the file is
  syntactically invalid (`AS $` with no closing tag), so the file cannot be applied at all — yet the
  function works in production. The `user_event_history` `SECURITY DEFINER` advisory is recorded as
  fixed in the requirements but is not fixed in the file. Nobody can tell which version is real.
- The file is not idempotent (bare `CREATE TABLE`/`CREATE POLICY` for most objects), so it only
  describes building a database from nothing.
- There is no way to review a schema change as a diff, no way to roll one back, and no way to bring
  up a local or staging database that matches production — which is also why the RLS test suite has
  never run.
- **Recommended replacement:** `supabase/migrations/` via the Supabase CLI, seeded with a baseline
  generated by diffing the live database, plus `supabase/config.toml` so `supabase start` works. See
  [the roadmap](../10-roadmap.md#stage-0--make-the-repo-collaborable).
